# 02. 수용 조건 = 테스트 시나리오

이슈의 수용 조건은 이 문서의 시나리오다. 시나리오 하나가 테스트 하나가 되고, 테스트 이름 앞에 시나리오 번호를 붙인다(`@DisplayName("LOGIN-03 ...")`). 이슈를 닫으려면 그 이슈의 시나리오가 모두 자동 테스트로 통과해야 한다.

- 형식: **주어진 상황** → **할 일** → **결과**
- 단계: `[단위]` 클래스 하나 · `[통합]` 샘플 앱 + 가짜 Keycloak 없이 Spring 컨텍스트 · `[E2E]` 샘플 앱 + **실제 Keycloak** + PostgreSQL을 HTTP로 (03 문서)
- 공통 값(E2E 기본): 화면 `https://app.kss.test`, API `https://api.kss.test`, 앱 이름 `demo`, 액세스 토큰 60초, 절대 상한 3분(테스트 설정)

---

## V3-01 빌드 기반 (Boot 4.1 · Security 7.1)

- **BUILD-01** `[단위]` 주어진 상황: 루트에서 → 할 일: `./gradlew build` → 결과: Boot 4.1.x BOM으로 모든 모듈이 컴파일되고 테스트가 통과한다.
- **BUILD-02** `[단위]` 주어진 상황: 빌드된 스타터 jar → 할 일: 의존성 트리를 본다 → 결과: `keycloak-client`, `reactor-netty`, `jjwt`, `spring-session-*`이 없다.
- **BUILD-03** `[단위]` 주어진 상황: CI → 할 일: PR을 올린다 → 결과: Java 17과 21에서 빌드·테스트가 돈다.
- **BUILD-04** `[단위]` 주어진 상황: CI → 할 일: Boot 4.2.x로 BOM을 바꿔 돌리는 작업 → 결과: 결과가 PR에 보인다(실패해도 머지를 막지 않는다).

## V3-02 검증 환경 (샘플 앱 + 실제 Keycloak)

- **E2E-01** `[E2E]` 주어진 상황: Docker가 있는 PC나 CI → 할 일: `./gradlew :integration-tests:servlet-app:e2eTest` → 결과: Keycloak(Testcontainers)과 PostgreSQL이 뜨고, realm 파일을 읽고, 시나리오 테스트가 돈다.
- **E2E-02** `[E2E]` 주어진 상황: Docker가 없는 곳 → 할 일: `KSS_E2E_KEYCLOAK_URL`, `KSS_E2E_DB_URL`을 주고 같은 명령 → 결과: 밖에 띄운 Keycloak·DB로 같은 테스트가 돈다.
- **E2E-03** `[E2E]` 주어진 상황: realm 파일 → 할 일: Keycloak에 넣는다 → 결과: client가 비공개, Standard flow만 켬, PKCE S256 강제, redirect URI 하나, back-channel 주소, Client Session Idle/Max, audience mapper, Full scope 끔으로 설정돼 있다.
- **E2E-04** `[E2E]` 주어진 상황: 테스트 사용자 → 할 일: 테스트 도구로 로그인 → 결과: Keycloak 로그인 화면 폼을 HTTP로 채워 로그인이 끝나고, 쿠키 상자에 앱 쿠키가 남는다(브라우저 없이).

- **CONF-02** `[통합]` 주어진 상황: `frontend.base-url`이 없다 → 할 일: 기동 → 결과: 기동이 실패하고, 빠진 설정 이름이 오류에 나온다.
- **CONF-03** `[통합]` 주어진 상황: 암호 키가 없거나 32바이트보다 짧다 → 할 일: 기동 → 결과: 기동이 실패한다.
- **CONF-04** `[통합]` 주어진 상황: `frontend.base-url`이 `https`가 아니고 `localhost`도 아니다 → 할 일: 기동 → 결과: 기동이 실패한다.
- **CONF-05** `[통합]` 주어진 상황: `session.store=memory` → 할 일: 기동 → 결과: 기동하지만 "여러 대에서 쓰면 안 된다" 경고가 찍힌다.

## V3-04 액세스 토큰 로컬 검증

- **JWT-01** `[단위]` 주어진 상황: 서명·iss·aud·azp·typ·exp가 맞는 토큰 → 할 일: 검증 → 결과: 통과하고 sub, sid를 꺼낸다.
- **JWT-02** `[단위]` 주어진 상황: alg가 `none` 또는 `HS256` → 할 일: 검증 → 결과: "갱신 안 함" 실패.
- **JWT-03** `[단위]` 주어진 상황: iss가 다르다 → 할 일: 검증 → 결과: "갱신 안 함" 실패.
- **JWT-04** `[단위]` 주어진 상황: aud에 내 client id가 없거나 azp가 다르다 → 할 일: 검증 → 결과: "갱신 안 함" 실패.
- **JWT-05** `[단위]` 주어진 상황: typ가 `ID`(ID 토큰을 at 자리에 넣음) → 할 일: 검증 → 결과: "갱신 안 함" 실패.
- **JWT-06** `[단위]` 주어진 상황: exp가 31초 지났다 / 29초 지났다 → 할 일: 검증 → 결과: 31초는 "만료(갱신 대상)", 29초는 통과.
- **JWT-07** `[단위]` 주어진 상황: nbf 또는 iat가 31초 넘게 미래 → 할 일: 검증 → 결과: "갱신 안 함" 실패.
- **JWT-08** `[단위]` 주어진 상황: 모르는 kid → 할 일: 1분 안에 두 번 검증 → 결과: JWKS를 한 번만 다시 받는다(5분에 한 번 제한).
- **JWT-09** `[E2E]` 주어진 상황: 로그인한 상태 → 할 일: `GET /api/me` 100번 → 결과: Keycloak의 introspect·userinfo·token 주소 호출이 0번이다(Keycloak 이벤트·접근 기록으로 확인).

## V3-05 세션 저장소와 암호

- **STORE-01** `[통합]` 주어진 상황: PostgreSQL에 스키마 → 할 일: 세션을 만든다 → 결과: 행에 sid 원문, 리프레시 토큰 원문이 없다(sid는 SHA-256, 토큰은 암호문).
- **STORE-02** `[단위]` 주어진 상황: 키 k1로 암호화한 행 → 할 일: 활성 키를 k2로 바꾸고 읽는다 → 결과: k1로 풀린다. 다음 갱신 때 k2로 다시 저장된다.
- **STORE-03** `[단위]` 주어진 상황: 암호문 1바이트를 바꾼다 → 할 일: 복호화 → 결과: 실패하고 로컬 로그아웃 처리된다(500이 아니다).
- **STORE-04** `[통합]` 주어진 상황: 같은 행을 두 트랜잭션이 잠그려 한다 → 할 일: 동시에 `lockForRefresh` → 결과: 하나가 끝날 때까지 다른 하나가 기다린다.
- **STORE-05** `[통합]` 주어진 상황: 절대 상한이나 리프레시 만료가 지난 행 3개, 살아 있는 행 2개 → 할 일: 정리 작업 실행 → 결과: 3개만 지워지고, 끝난 사유가 이벤트로 나간다.
- **STORE-06** `[통합]` 주어진 상황: 메모리 저장소 → 할 일: STORE-01·04·05와 같은 동작 → 결과: 같게 동작한다(같은 계약 테스트를 두 구현에 돌린다).
- **STORE-07** `[통합]` 주어진 상황: 앱이 `auth_session`에 열을 더 붙였다(NULL 허용) → 할 일: 로그인·갱신·로그아웃 → 결과: 정상 동작한다.

## V3-06 쿠키

- **COOKIE-01** `[E2E]` 주어진 상황: 로그인 성공 → 할 일: 콜백 응답의 Set-Cookie를 본다 → 결과: `__Host-demo_sid`, `__Host-demo_at`, `__Host-demo_csrf` 셋이 Secure, HttpOnly, SameSite=Lax, Path=/이고 Domain이 없다.
- **COOKIE-02** `[E2E]` 주어진 상황: 로그인 성공 → 할 일: 같은 응답을 본다 → 결과: `id_token`, `access_token`, `JSESSIONID` 쿠키가 없다. `__Host-demo_login`은 Max-Age=0으로 지워진다.
- **COOKIE-03** `[E2E]` 주어진 상황: 로그인 성공 → 할 일: 쿠키 수명을 본다 → 결과: at는 토큰 남은 시간 이하, sid·csrf는 절대 상한 남은 시간 이하.
- **COOKIE-04** `[단위]` 주어진 상황: 세션 끝 → 할 일: 쿠키 지우기 → 결과: 4개 모두 같은 이름·속성·Path로 Max-Age=0.
- **COOKIE-05** `[단위]` 주어진 상황: 앱 이름에 허용 안 되는 글자(공백, `;`) → 할 일: 기동 → 결과: 기동 실패.

## V3-07 로그인

- **LOGIN-01** `[E2E]` 주어진 상황: 쿠키 없음 → 할 일: `GET /api/me` → 결과: 401, 본문에 오류 코드와 로그인 주소(`/oauth2/authorization/keycloak`).
- **LOGIN-02** `[E2E]` 주어진 상황: 쿠키 없음 → 할 일: `GET /oauth2/authorization/keycloak?return=/items/3` → 결과: Keycloak 인가 주소로 302. 파라미터에 `code_challenge_method=S256`, `code_challenge`, `state`, `nonce`, `scope=openid`가 있고, `__Host-demo_login` 쿠키(5분)가 붙는다. HttpSession 쿠키는 없다.
- **LOGIN-03** `[E2E]` 주어진 상황: LOGIN-02 다음 → 할 일: Keycloak에서 로그인하고 콜백 → 결과: `https://app.kss.test/items/3`으로 302, 쿠키 3개, DB에 세션 행 1개.
- **LOGIN-04** `[E2E]` 주어진 상황: `return`이 `https://evil.example`, `//evil.example`, `/\evil`, `javascript:` → 할 일: 로그인 끝까지 → 결과: 모두 화면 주소 `/`로 돌아간다.
- **LOGIN-05** `[E2E]` 주어진 상황: 콜백의 state를 바꾼다 / login 쿠키를 지운다 / login 쿠키가 5분 지났다 → 할 일: 콜백 → 결과: 로그인 실패, 세션 행이 생기지 않는다.
- **LOGIN-06** `[E2E]` 주어진 상황: 예전 sid 쿠키가 있는 채로 다시 로그인 → 할 일: 콜백 → 결과: 예전 행은 지워지고 새 sid가 나온다(세션 고정 방지).
- **LOGIN-07** `[E2E]` 주어진 상황: 로그인 → 할 일: 콜백 처리 → 결과: ID 토큰이 쿠키에도 DB에도 저장되지 않는다.
- **LOGIN-08** `[E2E]` 주어진 상황: 같은 Keycloak에 client 둘(demo, demo2)과 샘플 앱 두 벌 → 할 일: demo에 로그인한 뒤 demo2 로그인 주소로 → 결과: Keycloak 로그인 화면 없이 demo2 세션이 따로 생기고, 두 앱 토큰의 sid가 같다.

## V3-08 요청 인증

- **REQ-01** `[E2E]` 주어진 상황: 로그인한 쿠키 → 할 일: `GET /api/me` → 결과: 200, 본문의 sub가 테스트 사용자다.
- **REQ-02** `[E2E]` 주어진 상황: 쿠키 없음 → 할 일: `GET /api/public/ping`(permit-all) → 결과: 200.
- **REQ-03** `[E2E]` 주어진 상황: 로그인한 쿠키 → 할 일: 요청 20번 → 결과: DB 세션 행 조회가 0번이다(SQL 기록으로 확인).
- **REQ-04** `[E2E]` 주어진 상황: at 쿠키의 서명을 망가뜨린다 → 할 일: `GET /api/me` → 결과: 401, 세션 행 삭제, 쿠키 삭제, 감사 로그 사유 `invalid_token`. Keycloak 갱신 호출 없음.
- **REQ-05** `[E2E]` 주어진 상황: 로그인한 쿠키 → 할 일: 요청 → 결과: 응답에 `JSESSIONID`가 없고 서버에 HttpSession이 만들어지지 않는다.
- **REQ-06** `[통합]` 주어진 상황: 사용자 `KeycloakPrincipalConverter` 빈 → 할 일: 요청 → 결과: 그 빈이 만든 principal과 권한이 컨트롤러에 들어온다.

## V3-09 갱신

- **REFRESH-01** `[E2E]` 주어진 상황: 로그인 후 액세스 토큰 만료(60초 대기 또는 at 쿠키 삭제) → 할 일: `GET /api/me` → 결과: 200, 새 at 쿠키, 행의 `refreshed_at`·암호문이 바뀐다. 화면은 갱신을 모른다.
- **REFRESH-02** `[E2E]` 주어진 상황: 만료 상태 → 할 일: 같은 sid로 요청 5개를 동시에 → 결과: 모두 200, Keycloak 갱신 호출은 1번.
- **REFRESH-03** `[E2E]` 주어진 상황: 절대 상한(테스트 3분) 지남 → 할 일: 요청 → 결과: Keycloak을 부르지 않고 401, 행 삭제, 사유 `absolute`.
- **REFRESH-04** `[E2E]` 주어진 상황: Keycloak 관리 API로 사용자 세션을 끊는다(또는 계정 비활성화) → 할 일: at 만료 뒤 요청 → 결과: Keycloak이 `invalid_grant`, 앱은 401, 행·쿠키 삭제, 사유 `refresh_failed`.
- **REFRESH-05** `[E2E]` 주어진 상황: Client Session Idle(테스트 2분) 동안 요청 없음 → 할 일: 요청 → 결과: 401, 사유 `refresh_failed` 또는 `idle`(리프레시 만료 시각으로 판단).
- **REFRESH-06** `[E2E]` 주어진 상황: Keycloak을 멈춘다 → 할 일: at 만료 뒤 요청 → 결과: 503, 행은 그대로. Keycloak을 다시 켜면 다음 요청은 200.
- **REFRESH-07** `[E2E]` 주어진 상황: 만료 상태 → 할 일: `X-Background: 1` 헤더로 요청 → 결과: 갱신하지 않고 401, 행은 그대로.
- **REFRESH-08** `[단위]` 주어진 상황: 갱신 응답 토큰의 sub 또는 sid가 행과 다르다 → 할 일: 갱신 → 결과: 401, 행 삭제, 사유 `invalid_token`.
- **REFRESH-09** `[통합]` 주어진 상황: 다른 요청이 5초 전에 갱신했다 → 할 일: 잠금을 얻은 뒤 → 결과: Keycloak을 다시 부르지 않고 행의 사용자로 요청을 처리한다.

## V3-10 CSRF · Origin · CORS

- **CSRF-01** `[E2E]` 주어진 상황: 로그인 → 할 일: `GET /api/csrf` → 결과: 200, 본문에 헤더 이름 `X-XSRF-TOKEN`, 칸 이름 `_csrf`, 토큰.
- **CSRF-02** `[E2E]` 주어진 상황: 로그인 → 할 일: 토큰 없이 `POST /api/items` → 결과: 403.
- **CSRF-03** `[E2E]` 주어진 상황: 로그인 → 할 일: CSRF-01 토큰을 헤더에 넣고 `POST /api/items` → 결과: 201.
- **CSRF-04** `[E2E]` 주어진 상황: 사용자 A의 토큰 → 할 일: 사용자 B 쿠키로 `POST` → 결과: 403(sid 서명 불일치).
- **CSRF-05** `[E2E]` 주어진 상황: 토큰 맞음 → 할 일: Origin `https://evil.kss.test`로 `POST` → 결과: 403. Origin이 없고 Referer도 없으면 403. Referer가 화면 주소면 통과.
- **CSRF-06** `[E2E]` 주어진 상황: 로그인 성공 → 할 일: 로그인 전 토큰으로 `POST` → 결과: 403(로그인하면 토큰이 바뀜).
- **CSRF-07** `[E2E]` 주어진 상황: HTML 폼 → 할 일: `_csrf` 숨은 칸으로 `POST /logout` → 결과: 통과.
- **CORS-01** `[E2E]` 주어진 상황: 쿠키 없음 → 할 일: Origin 화면 주소로 `OPTIONS /api/items`(사전 확인) → 결과: 200, `Access-Control-Allow-Origin`이 화면 주소, `Allow-Credentials: true`, 허용 헤더에 `X-XSRF-TOKEN`.
- **CORS-02** `[E2E]` 주어진 상황: 다른 Origin → 할 일: 사전 확인 → 결과: 허용 헤더가 없다. `*`나 받은 Origin을 그대로 돌려주지 않는다.

## V3-11 로그아웃

- **LOGOUT-01** `[E2E]` 주어진 상황: 로그인 → 할 일: CSRF 토큰과 `POST /logout` → 결과: Keycloak에 리프레시 토큰 로그아웃 호출, 행 삭제, 쿠키 4개 삭제, `https://app.kss.test/logged-out`으로 302. Keycloak SSO 세션이 끝난다(관리 API로 확인).
- **LOGOUT-02** `[E2E]` 주어진 상황: 리프레시 토큰을 Keycloak에서 미리 끊었다 → 할 일: `POST /logout` → 결과: 행·쿠키 삭제, Keycloak 로그아웃 주소로 302, 파라미터에 `client_id`, `post_logout_redirect_uri`, `state`가 있고 `id_token_hint`는 없다.
- **LOGOUT-03** `[E2E]` 주어진 상황: 로그인 → 할 일: `GET /logout` → 결과: 로그아웃되지 않는다(405 또는 403).
- **LOGOUT-04** `[E2E]` 주어진 상황: 로그인 → 할 일: CSRF 없이 `POST /logout` → 결과: 403, 세션 그대로.
- **LOGOUT-05** `[E2E]` 주어진 상황: 이미 로그아웃(쿠키 없음) → 할 일: `POST /logout` → 결과: 화면 로그아웃 주소로 302(오류 없음).
- **LOGOUT-06** `[E2E]` 주어진 상황: `revoke-refresh-token-on-local-logout=true` → 할 일: 절대 상한으로 로컬 로그아웃 → 결과: Keycloak에 토큰 폐기 호출이 간다. 기본값(false)이면 안 간다.

## V3-12 back-channel 로그아웃

- **BCL-01** `[E2E]` 주어진 상황: demo와 demo2에 같은 사람이 로그인 → 할 일: demo에서 `POST /logout` → 결과: Keycloak이 demo2에 logout_token을 보내고, demo2의 행이 지워진다. demo2는 at가 끝난 뒤 다음 요청에서 401.
- **BCL-02** `[E2E]` 주어진 상황: 서명이 틀린 logout_token / aud가 다른 토큰 / events가 없는 토큰 / nonce가 있는 토큰 → 할 일: back-channel 주소로 POST → 결과: 400, 행은 그대로.
- **BCL-03** `[E2E]` 주어진 상황: 행이 이미 없음 → 할 일: 맞는 logout_token → 결과: 200.
- **BCL-04** `[E2E]` 주어진 상황: back-channel 주소 → 할 일: CSRF·Origin 없이 POST → 결과: CSRF·Origin 검사로 막히지 않는다(logout_token 서명으로 보호).
