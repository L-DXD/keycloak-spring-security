# 01. v3 설계

v3는 v2를 고치는 판이 아니라 새로 짜는 판이다. 라이브러리의 컨셉(아래 1절)은 그대로 두고, 안쪽 동작을 "BFF + JWT 쿠키 + DB 세션 행" 인증 방식으로 바꾼다.

표시: **[정함]** 이봉승이 정한 것 · **[제안]** 아직 결정 전, 이 판은 제안대로 진행 · **[확인 필요]** 실제 환경에서 확인할 것

---

## 1. 그대로 두는 컨셉 [정함]

v2 README 4·5장의 원칙을 그대로 지킨다. 지켜졌는지는 아키텍처 테스트(ArchUnit)로 빌드마다 확인한다(시나리오 EXT-01~05).

| # | 컨셉 | v3에서 지키는 법 |
|---|---|---|
| 1 | **커스텀은 열어 둔다.** 자동 설정의 빈마다 `@ConditionalOnMissingBean`을 붙여, 사용자가 같은 타입(또는 이름) 빈을 올리면 그것을 쓴다 | 4절 확장 지점 표의 빈은 모두 갈아끼울 수 있다. 빠진 빈이 없는지 테스트한다 |
| 2 | `Customizer<T>`로 덧붙인다 | `KeycloakHttpConfigurer`가 부분마다 `Customizer`를 받는다(로그인, CSRF, CORS, 로그아웃). 쿠키는 빈으로 바꾼다(D23) |
| 3 | 보안상 꼭 필요한 곳이 아니면 `final`을 쓰지 않는다 | 공개 클래스에 `final`이 있으면 테스트가 실패한다. 예외는 값 객체(record)와 암호 처리 클래스뿐이다 |
| 4 | core(순수 Java)와 Servlet·Reactive 구현, 환경별 스타터를 나눈다 | 모듈 이름과 artifactId는 v2와 같다. core는 `jakarta.servlet`, `org.springframework.web`을 import하지 않는다 |
| 5 | 스타터 하나만 넣으면 설정 몇 줄로 돌아간다(Zero-config) | 필수 설정은 issuer, client id/secret, 화면 주소, 암호 키, DB뿐이다. 빠지면 기동 때 알려 준다 |

## 2. 버전 기준 [정함]

| 항목 | v3 기준 | v2 |
|---|---|---|
| Spring Boot | 4.1.x (Boot가 고르는 버전 그대로) | 3.5.9 |
| Spring Security | 7.1.x (Boot 4.1이 고르는 버전) | 6.5.x |
| Spring Framework | 7.0.x | 6.2.x |
| Java | 17 이상 (빌드 대상 17) [제안] | 17 |
| Gradle | 9.x [제안] | 8.5 |
| Keycloak (검증) | 26.8.x 최신 + 실제 운영 서버 판 [확인 필요] | - |

Boot 4.2(Security 7.2)가 나오면 CI에서 같이 돌려 본다. 같은 4.x라 코드는 그대로 가는 것을 목표로 한다.

v2 코드를 BOM만 4.1.2로 바꿔 컴파일해 보면 web·webflux 모듈에서 오류 3건이 먼저 나온다(`KeycloakHttpConfigurer`의 사라진 클래스 1건, `ReactiveAuthorizationManager.check` 제거 2건). 스타터 모듈은 이 오류 때문에 컴파일까지 가지 못해서, 실제로 고칠 곳은 더 있다. 동작 방식이 바뀌므로 올리기보다 새로 짠다.

## 3. 무엇이 바뀌나 (v2 → v3)

### 3-1. 인증 방식

| 항목 | v2 | v3 |
|---|---|---|
| 요청 인증 | 요청마다 Keycloak introspect + UserInfo 호출 | `at` 쿠키의 액세스 토큰(JWT)을 로컬에서 검증. Keycloak도 DB도 부르지 않는다 |
| 서버 상태 | HttpSession(메모리 또는 Redis)에 토큰 보관 | HttpSession을 만들지 않는다. 앱 DB의 세션 행에 리프레시 토큰만 암호화해서 둔다 |
| 쿠키 | `access_token`, `id_token` (이름 고정) | `__Host-{app}_sid` · `_at` · `_csrf` + 로그인 중에만 `_login` |
| ID 토큰 | 쿠키에 두고 요청마다 사용 | 저장하지 않는다. 로그인 때 Spring이 표준대로 확인만 한다 |
| 갱신 | introspect가 실패하면 갱신 | exp가 지났을 때만 갱신. 다른 검증 실패는 바로 로컬 로그아웃 |
| 동시 갱신 | 따로 막지 않음 | 세션 행 잠금으로 한 번만 갱신 |
| 세션 상한 | 미사용 30분(`session.timeout`) | 절대 상한(기본 12시간, 갱신 때 확인). 미사용은 Keycloak client의 Client Session Idle에 맡긴다 |
| CSRF | 세션 저장 토큰(기본) 또는 쿠키 | sid로 HMAC 서명한 double-submit 토큰 + Origin 확인. 토큰은 `GET /api/csrf`로 준다 |
| CORS | 없음 | 화면 origin 하나에만, 쿠키 허용 |
| PKCE | 없음 | S256 항상 |
| 로그인 임시 정보 | HttpSession | 암호화 쿠키(`_login`, 5분) |
| 로그아웃 | 결과와 상관없이 OIDC 로그아웃 주소로 이동 | 리프레시 토큰으로 Keycloak 로그아웃. 성공하면 화면으로, 실패할 때만 OIDC 로그아웃 주소로 |
| back-channel 로그아웃 | 색인 세션 저장소가 있어야 동작(메모리면 무동작) | `kc_sid`로 세션 행 삭제. 저장소와 상관없이 동작 |

### 3-2. 빼는 것 [제안]

v3 범위는 "브라우저 앱의 로그인"이다. 아래는 v3에서 뺀다. 필요하면 확장 지점으로 직접 붙이거나, 요청이 있을 때 3.x에서 다시 넣는다.

| v2 기능 | v3 | 이유 |
|---|---|---|
| Basic 인증 | 뺌 | 머신 클라이언트는 Keycloak service account로 받는 것이 맞다 |
| 토큰 발급 API(`/auth/token`, `/auth/refresh`, `/auth/logout`) | 뺌 | 비밀번호를 앱이 받는 방식(Direct access grants)은 쓰지 않는다 |
| Rate limit | 뺌 | 로그인은 Keycloak 화면에서 한다. 앱 API 제한은 게이트웨이나 앱이 정한다 |
| Keycloak Authorization Services 인가(`KeycloakAuthorizationManager`) | 뺌 | 인가는 앱이 한다 |
| introspect·UserInfo 호출 | 뺌 | 로컬 JWT 검증으로 바꾼다 |
| Redis·HttpSession 세션 저장소 | 뺌 | 세션 행(JDBC)으로 바꾼다. 다른 저장소는 `KeycloakSessionStore`를 구현해 붙인다 |
| 역할 → 권한 매핑 | 확장 지점만 둔다(기본은 권한 없음) | 토큰에 역할을 싣지 않는 것이 기본이다. 3.1에서 선택 기능으로 다시 넣을 수 있다 |
| `io.github.l-dxd:keycloak-client` 의존 | 뺌 | 갱신·로그아웃 호출은 Spring Security OAuth2 Client와 `RestClient`로 한다. reactor-netty, jjwt, Jackson 2가 따라오지 않는다 |

남기는 것: MDC 로깅(사내 표준 위임 구조 포함), 오류 응답 형식(`{"code","message"}` JSON. `error.*` 설정은 빼고 빈으로 바꾼다, 4-5), 감사 로그.

### 3-3. Servlet 먼저 [제안]

3.0.0은 Servlet(Spring MVC)만 낸다. WebFlux 모듈은 3.1.0에서 같은 core로 다시 짠다. 모듈과 artifactId 자리는 그대로 둔다.

## 4. 구조

### 4-1. 모듈

| 모듈 (artifactId 그대로) | 담는 것 |
|---|---|
| `keycloak-spring-security-core` | 설정 값 객체, 세션 모델과 `KeycloakSessionStore`(JDBC·메모리 구현과 스키마 SQL 포함), 정리 작업, 암호(`TokenCipher`, sid 해시, CSRF 서명), 토큰 클레임 규칙, 오류 코드, 세션 이벤트, MDC 키. Spring Web·Servlet 의존 없음 (JDBC 저장소를 WebFlux와 같이 쓰려고 core에 둔다, D16) |
| `keycloak-spring-security-web` | Servlet 필터와 처리기: 요청 인증, 갱신, 로그인 성공·실패, 로그인 임시 쿠키 저장소, CSRF 저장소, `/api/csrf`, Origin 확인, 로그아웃, back-channel 로그아웃, 쿠키 쓰기, `KeycloakHttpConfigurer` |
| `keycloak-spring-security-web-starter` | 자동 설정, 설정 바인딩(`keycloak.security.*`), 기동 때 설정·세션 테이블 검사 |
| `keycloak-spring-security-webflux(-starter)` | 3.1.0 (3.0.0에서는 빌드에서 뺀다) |
| `integration-tests/servlet-app` | 검증용 샘플 앱(가상 프로젝트). 03 문서 |

패키지 루트는 `com.ids.keycloak.security`, groupId는 `io.github.l-dxd` 그대로다.

### 4-2. 요청 한 번의 순서 (Servlet)

```text
MdcRequestFilter (보안 체인 맨 앞) 요청 MDC(traceId 등) 넣기, 응답 X-Request-Id, 끝나면 넣은 키만 지움
→ CorsFilter                     다른 화면 Origin은 여기서 403, 사전 확인(OPTIONS)은 여기서 응답
→ KeycloakOriginFilter          상태 바꾸는 요청의 Origin/Referer 확인 (Origin 없음, API 자신의 Origin)
→ CsrfFilter                     sid 서명 double-submit 확인
→ KeycloakCsrfTokenEndpointFilter GET /api/csrf 응답
→ KeycloakAccessTokenFilter      at 쿠키 JWT 로컬 검증 → SecurityContext
     ├ exp 만료·쿠키 없음 → KeycloakRefreshService (세션 행 잠금 → Keycloak 갱신)
     └ 그 밖의 검증 실패 → 로컬 로그아웃(행·쿠키 삭제) → 401
→ MdcAuthenticationFilter        사용자 MDC(userId·username·sessionId) 넣기
→ AuthorizationFilter            permit-all 경로 / 그 밖은 로그인 필요
```

로그인(`/oauth2/authorization/keycloak`, `/login/oauth2/code/keycloak`)은 Spring Security `oauth2Login`을 쓰고, 저장소와 처리기만 바꿔 끼운다. 로그아웃(`POST /logout`)과 back-channel 로그아웃(`/logout/connect/back-channel/keycloak`)은 라이브러리 처리기로 받는다.

### 4-3. 확장 지점 (커스텀 열어 두기)

모두 자동 설정에 `@ConditionalOnMissingBean`으로 올린다. 사용자가 같은 빈을 올리면 그것을 쓴다.

| 빈 (타입) | 기본 구현 | 바꾸는 예 |
|---|---|---|
| `KeycloakSessionStore` | `JdbcKeycloakSessionStore`(PostgreSQL, H2) · 설정으로 `InMemoryKeycloakSessionStore` | 다른 DB, 테이블 구조가 다른 앱 |
| `KeycloakAccessTokenValidator` (`JwtDecoder` 감싼 것) | JWKS + RS256 + iss + aud/azp + typ + 시간 오차 30초. 결과는 통과·만료(갱신)·실패(로컬 로그아웃)·JWKS 못 받음(503) | 검증 규칙 추가 |
| `JwkSetFetcher` | JWKS를 HTTP로 받기(연결 2초·읽기 3초). 모르는 kid면 다시 받되 1분에 한 번 | 프록시, 타임아웃 |
| `KeycloakPrincipalConverter` | `Jwt` → `KeycloakPrincipal`(sub, sid, azp, 선택 클레임), 권한 없음 | 역할을 권한으로, 앱 사용자 테이블 조회 |
| `KeycloakTokenClient` | `DefaultKeycloakTokenClient`: Spring OAuth2 Client로 refresh_token 요청(연결 2초·읽기 5초, 리다이렉트 안 따라감). `invalid_grant`만 세션을 끝낼 오류로 보고, 연결 실패·5xx·`invalid_client`는 503으로 돌린다. 로그아웃(`end_session_endpoint`에 refresh_token)과 폐기(`revocation_endpoint`)도 같은 client 인증(Basic·post)으로 부른다. 주소는 OIDC 설명 문서에서, 없으면 `{issuer}/protocol/openid-connect/logout`·`/revoke` | 프록시, 타임아웃, 재시도 |
| `KeycloakRefreshService` | 갱신 순서(4-6). `refreshExpiresAt(...)`을 덮어쓸 수 있다 | 리프레시 만료를 다르게 셈 |
| `TokenCipher` | AES-256-GCM, 키 id로 교체 | KMS·HSM |
| `KeycloakCookieWriter` | `__Host-{app}_*`, Secure, HttpOnly, SameSite=Lax, Path=/ | 쿠키 이름 규칙 |
| `CsrfTokenRepository` | `SignedDoubleSubmitCsrfTokenRepository`: csrf 쿠키의 토큰을 sid 서명이 맞을 때만 쓴다(4-7) | - |
| `CorsConfigurationSource` (이름 `keycloakCorsConfigurationSource`) | `KeycloakCors`: 화면 origin 하나, 쿠키 허용, 허용 헤더 `Content-Type`·`Accept`·`X-Requested-With`·`X-XSRF-TOKEN`·`X-Background`. Origin 확인도 이 허용 목록을 쓴다. Spring MVC의 다른 CORS 빈과 섞이지 않게 이름으로 찾는다 | origin·헤더 더하기 |
| (설정기 메서드) `originFilter`, `csrfTokenEndpointFilter`, `csrfTokenRequestHandler`, `serverCallbacks` | Origin 확인 필터, `/api/csrf` 필터, Xor 처리기, 확인에서 뺄 주소(back-channel 로그아웃, OIDC 콜백). 필터는 빈이 아니다. `/logout`의 GET 등은 `KeycloakLogoutMethodFilter`가 405로 막는다 | 설정기 상속 |
| `LoginReturnPathResolver` | `return` 파라미터, 상대 경로만 | 경로 화이트리스트 |
| `KeycloakLoginSuccessHandler` | 세션 행 만들기 → sid·at·csrf 쿠키 → 화면 주소로 302. 메서드(`endPreviousSession`, `writeCookies`, `redirectUrl`)를 덮어쓸 수 있다 | 로그인 직후 앱 사용자 테이블 갱신 |
| `KeycloakLoginFailureHandler` | login 쿠키를 지우고 화면 `/?login_error=코드`로 302 | 오류 화면 주소 |
| `KeycloakAuthenticationEntryPoint` / `KeycloakAccessDeniedHandler` / `KeycloakErrorResponseWriter` | 401·403·503 JSON | 앱 오류 형식 |
| `KeycloakSessionEventListener` | 감사 로그 `KeycloakSessionAuditLogger`(로거 `com.ids.keycloak.security.audit`, 토큰 값 없음, 사용자 id 앞 8자). 이 빈을 올리면 기본 감사 로그 대신 그것이 받는다. Spring `@EventListener`로도 받는다 | 감사 테이블 저장 |
| `KeycloakLocalLogoutHandler` | sid 쿠키의 행 삭제 → 쿠키 4개 삭제 → ENDED 이벤트(사유). Keycloak은 부르지 않는다. 토큰 검증 실패·갱신 실패가 쓴다 | 로컬 로그아웃 때 앱 캐시 비우기 |
| `KeycloakLogoutHandler` | `POST /logout`: 행 삭제 → 쿠키 4개 삭제 → ENDED(`logout`) → 행의 리프레시 토큰으로 Keycloak 로그아웃. 결과(세션 없음·성공·실패)를 요청 속성에 남긴다 | 로그아웃 때 앱 캐시 비우기 |
| `KeycloakLogoutSuccessHandler` | 세션이 없었거나 Keycloak 로그아웃이 됐으면 화면 로그아웃 주소로 302, 실패했으면 Keycloak 로그아웃 주소(`client_id`·`post_logout_redirect_uri`·`state`, `id_token_hint` 없음)로 302. `oidcLogoutUrl(...)`을 덮어쓸 수 있다 | 로그아웃 뒤 주소 |
| `KeycloakBackChannelLogoutHandler` | 검증된 `logout_token`의 `sid`로 세션 행을 모두 지우고 행마다 ENDED(`backchannel_logout`). `sid`가 없으면 400(D20) | 로그아웃 때 앱 캐시 비우기 |
| `LoggingContextAccessor` | `WebMdcContextAccessor`: SLF4J MDC. 넣은 키만 기억했다가 그 키만 지운다 | 사내 로깅 표준(다른 키 이름, 다른 컨텍스트) |
| `LoggingValueSanitizer` | `DefaultPiiMaskingSanitizer`: JWT·Bearer·OAuth2 파라미터·주민번호·카드·이메일·전화 가리기. 쿼리·User-Agent·username에 쓴다. 가리지 않으려면 `NoOpLoggingValueSanitizer` | 사내 마스킹 규칙 |
| (설정기 메서드) `mdcRequestFilter`, `mdcAuthenticationFilter` | MDC 필터 두 개. `MdcRequestFilter.putRequest`·`traceId`, `MdcAuthenticationFilter.putUser`를 덮어써 키를 더한다 | 설정기 상속 |
| `KeycloakRefreshTokenRevoker` | `revoke-refresh-token-on-local-logout=true`일 때만 로컬 로그아웃(사유 `absolute`·`invalid_token`)한 세션의 리프레시 토큰을 Keycloak에서 폐기한다. 실패해도 경고만 | - |
| `KeycloakSessionCleaner` | `session.cleanup-interval`마다 데몬 스레드 하나로 끝난 행을 500개씩 지우고 ENDED 이벤트(사유 `absolute`·`idle`)를 낸다 | DB 배치 작업으로 대신 |
| `Clock` (이름 `keycloakSecurityClock`) | 시스템 시계 | 테스트 |
| `SecurityFilterChain` (이름 `keycloakSecurityFilterChain`) | 기본 체인. 모든 주소를 받고 맨 뒤(`LOWEST_PRECEDENCE`)에 선다. 앱이 다른 체인을 더해도 빠지지 않는다(D24) | 같은 이름의 빈, 또는 `auto-filter-chain: false` + 사용자 체인에 `KeycloakHttpConfigurer` |

표에 없는 자동 설정 빈(설정 값 `KeycloakSecuritySettings`, Keycloak 정보 `KeycloakProvider`, CSRF 서명기, 로그인 요청 저장소, 이벤트 발행기, 지연 초기화 제외 `keycloakSecurityEagerInit`)도 같다. 자동 설정의 `@Bean`을 리플렉션으로 모두 찾아 빈마다 바꿔 끼우는 테스트가 있다(EXT-01·05).

```java
@Bean
SecurityFilterChain api(HttpSecurity http) throws Exception {
    return http
        .securityMatcher("/api/**", "/oauth2/**", "/login/oauth2/**", "/logout/**")
        .authorizeHttpRequests(a -> a.requestMatchers("/api/public/**").permitAll().anyRequest().authenticated())
        .with(KeycloakHttpConfigurer.keycloak(), Customizer.withDefaults())
        .build();
}
```

설정기는 부분마다 `Customizer`를 받아 라이브러리 설정 뒤에 부른다(같은 값을 주면 사용자 것이 이긴다).

```java
.with(KeycloakHttpConfigurer.keycloak()
        .login(l -> ...)                                        // OAuth2LoginConfigurer
        .csrf(c -> c.ignoringRequestMatchers("/api/webhooks/**")) // CsrfConfigurer
        .cors(c -> ...)                                         // CorsConfigurer
        .logout(l -> l.addLogoutHandler(appCacheEvictor)),      // LogoutConfigurer
    Customizer.withDefaults())
```

기본 체인은 이름으로만 빠진다(타입으로 빠지면 앱이 `/actuator/**` 체인 하나만 더해도 나머지 주소가 로그인 없이 열린다. v2 1.5.0에서 고친 fail-open, D24). 앱 체인이 일부 주소만 받으면(`securityMatcher`) 기본 체인이 그 뒤에서 나머지를 지킨다. 앱 체인이 모든 주소를 받으려면 빈 이름을 `keycloakSecurityFilterChain`으로 하거나 `keycloak.security.auto-filter-chain=false`로 기본 체인을 끈다. 둘 다 안 하면 Spring Security가 "모든 주소를 받는 체인이 둘"이라며 기동을 멈춘다(EXT-06).

쿠키는 로그인 성공·갱신·로그아웃 처리기(체인 밖의 빈)가 같이 쓰므로 `Customizer`가 아니라 `KeycloakCookieWriter` 빈으로 바꾼다(D23). CORS 허용 목록은 Origin 확인과 같이 쓰므로 이름 `keycloakCorsConfigurationSource` 빈으로 바꾼다. 값은 `keycloak.security.*`에서 바꾸고, 필터 자체를 바꾸려면 설정기를 상속해 보호 메서드를 덮어쓴다. 사용자 체인에서도 로그인·요청 인증·갱신·로그아웃이 기본 체인과 같이 된다(EXT-02).

### 4-4. 요청 인증 (#84)

`KeycloakAccessTokenFilter`는 빈이 아니다(서블릿 필터로 따로 등록되어 보안 체인 밖에서 돌지 않게). `KeycloakHttpConfigurer`가 Basic 인증 자리 앞에 넣고, 바꾸려면 설정기의 `accessTokenFilter(...)`를 덮어쓰거나 필터가 쓰는 빈을 바꾼다.

| at 쿠키 검증 결과 | 하는 일 |
|---|---|
| 통과 | `KeycloakPrincipalConverter`가 만든 인증을 보안 컨텍스트(요청 속성)에 넣는다. 기본은 `KeycloakAuthenticationToken`(principal `KeycloakPrincipal`: sub·sid·azp·클레임, credentials는 `Jwt`, 권한 없음). 세션 행을 보지 않는다 |
| 쿠키 없음, 만료 | sid 쿠키가 있으면 갱신한다(4-6). sid 쿠키가 없거나 sid 모양이 아니면 로그인 안 한 채로 넘긴다 |
| 그 밖의 실패(서명, iss, aud, typ …) | 로컬 로그아웃(`KeycloakLocalLogoutHandler`, 사유 `invalid_token`) 뒤 로그인 안 한 채로 넘긴다. 갱신하지 않는다 |
| JWKS를 못 받음 | 로그아웃하지 않고 503 `KEYCLOAK_UNAVAILABLE` |

로그인 필요 여부는 뒤의 인가가 정한다(permit-all 경로는 그대로 통과, 그 밖은 401). 앞에서 다른 방식으로 이미 인증했으면 건드리지 않는다. 변환기가 `AuthenticationException`을 던지면 그 요청만 로그인 안 한 것으로 본다. 컨트롤러는 `@AuthenticationPrincipal KeycloakPrincipal user`로 받는다. `getName()`은 sub다.

### 4-5. 로그인과 오류 응답 (#83)

로그인은 Spring Security `oauth2Login`에 아래만 바꿔 끼운다. HttpSession은 만들지 않는다(보안 컨텍스트는 요청 속성에만, 요청 캐시 없음). `sessionCreationPolicy(STATELESS)`는 쓰지 않는다: 설정 순서 때문에 `SessionManagementFilter`가 켜져 로그인한 요청마다 세션을 만든다(REQ-05에서 발견).

| 단계 | 하는 일 |
|---|---|
| `GET /oauth2/authorization/keycloak?return=/경로` | PKCE S256·state·nonce를 만들고, 인가 요청과 돌아갈 경로를 `__Host-{app}_login` 쿠키(5분)에 암호화해 담는다(`KeycloakAuthorizationRequestRepository`, HKDF 용도 `login-state`). 만든 시각은 쿠키 안에 두고 서버 시계로 5분을 다시 본다 |
| 돌아갈 경로 | `/`로 시작하는 상대 경로만. `//`, `\`, 제어 문자, 2048자 넘는 값, 절대 주소는 모두 `/` |
| `GET /login/oauth2/code/keycloak` | Spring이 code 교환과 ID 토큰(서명·nonce)을 확인한다. UserInfo는 부르지 않는다. 받은 토큰은 요청 안에서만 쓰고 어디에도 두지 않는다 |
| 성공 | 액세스 토큰을 로컬 검증 규칙으로 다시 보고(sub·sid 필수), 예전 sid 쿠키의 행을 지운 뒤(사유 `relogin`) 새 행을 만든다. sid·csrf 쿠키는 절대 상한까지, at 쿠키는 토큰 남은 시간까지. 화면 주소 + 돌아갈 경로로 302 |
| 실패 | login 쿠키를 지우고 화면 `/?login_error=코드`로 302. 세션 행은 만들지 않는다 |

로그인 실패 코드: `invalid_state`(login 쿠키 없음·5분 지남·state 다름), `access_denied`(Keycloak에서 취소), `invalid_token`(받은 토큰이 검증 규칙에 맞지 않음), `login_failed`(그 밖).

401·403·503 본문은 `KeycloakErrorCode` 하나로 정한다. 401에만 로그인 주소가 붙는다(context-path 포함).

```json
{"code":"AUTHENTICATION_REQUIRED","message":"로그인이 필요합니다.","loginUrl":"/oauth2/authorization/keycloak"}
{"code":"ACCESS_DENIED","message":"..."}
{"code":"KEYCLOAK_UNAVAILABLE","message":"..."}
```

CSRF 토큰 값은 `키id.난수.HMAC-SHA256(sid, 난수)`이다(HKDF 용도 `csrf`). 로그인 때 csrf 쿠키에 넣는다. 확인은 4-7.

### 4-6. 갱신 (#85)

at 쿠키가 없거나 만료면 `KeycloakAccessTokenFilter`가 `KeycloakRefreshService`를 부른다. 화면은 갱신을 모른다(리다이렉트 없이 원래 응답).

1. sid 해시로 세션 행을 잠근다(`SELECT … FOR UPDATE`, DB 연결 하나). 같은 세션의 동시 요청은 여기서 줄을 선다.
2. 절대 상한이 지났으면 사유 `absolute`, 리프레시 만료(Keycloak Client Session Idle)가 지났으면 사유 `idle`로 행을 지운다. 이 둘은 Keycloak을 부르지 않는다.
3. 이 인스턴스가 `refresh-reuse-window`(기본 10초) 안에 이 행을 갱신했고 그 뒤 다른 곳에서 갱신하지 않았으면(행의 `refreshed_at`이 같음) 그 액세스 토큰을 다시 쓴다. Keycloak은 부르지 않는다.
4. 리프레시 토큰을 푼다. 못 풀면 사유 `decryption_failed`.
5. Keycloak에 refresh_token 요청. `invalid_grant`면 사유 `refresh_failed`. 닿지 못했거나 그 밖의 오류면 행을 두고 503 `KEYCLOAK_UNAVAILABLE`.
6. 새 액세스 토큰을 로컬 검증 규칙으로 보고, sub·sid가 행과 같은지 본다. 다르면 사유 `invalid_token`. JWKS를 못 받으면 새 리프레시 토큰만 저장하고 503.
7. 새 리프레시 토큰(활성 키로 암호화), 리프레시 만료(토큰 exp → `refresh_expires_in` → 예전 값, 절대 상한까지), `refreshed_at`을 쓴다.
8. 잠금이 풀린 뒤 이벤트(REFRESHED 또는 ENDED+사유)를 낸다.

| 결과 | 필터가 하는 일 |
|---|---|
| 갱신함, 다시 씀 | 새 at 쿠키(수명은 토큰 exp와 절대 상한 가운데 이른 쪽까지)를 쓰고 그 토큰의 사용자로 요청을 이어 간다 |
| 세션 끝남 | 쿠키 4개를 지우고 로그인 안 한 채로 넘긴다(보통 401) |
| Keycloak에 닿지 않음 | 503. 쿠키·행은 그대로 |

`background-header`(기본 `X-Background`)가 붙은 요청은 갱신하지 않는다. 화면이 주기적으로 부르는 요청 때문에 세션이 끝없이 늘어나지 않게 하려는 것이다. 다른 인스턴스가 방금 갱신한 경우에는 그 토큰을 모르므로 한 번 더 갱신한다(Keycloak 호출 1번 더, 드묾).

### 4-7. CSRF·Origin·CORS (#86)

| 단계 | 하는 일 |
|---|---|
| CORS | 화면 origin 하나만 허용하고 쿠키를 허용한다(`Access-Control-Allow-Credentials: true`). `*`나 받은 Origin을 그대로 돌려주지 않는다. 사전 확인은 로그인 없이 200. 다른 화면 Origin이 붙은 요청은 사전 확인이든 실제 요청이든 403(허용 헤더 없음) |
| Origin 확인 | GET·HEAD·OPTIONS·TRACE 말고는 `Origin`이, 없으면 `Referer`의 origin이 CORS 허용 목록에 있어야 한다. 둘 다 없거나 API 자신의 Origin이면 403 `ORIGIN_NOT_ALLOWED`. back-channel 로그아웃과 OIDC 콜백은 뺀다 |
| CSRF 토큰 | 원본은 `__Host-{app}_csrf` 쿠키(HttpOnly)에 있고, 화면은 `GET /api/csrf`로 받는다. 이 요청의 sid 쿠키로 서명이 맞는 쿠키만 쓴다(다른 사람의 csrf 쿠키를 심어도 안 통함). 로그인 전에는 빈 값에 묶은 토큰을 주고, 로그인하면 로그인 처리기가 새 sid에 묶은 토큰을 쓴다(Spring의 로그인 때 토큰 다시 만들기는 끈다) |
| 보내는 법 | 헤더 `X-XSRF-TOKEN` 또는 폼 칸 `_csrf`. 처리기는 Spring 기본(Xor)이라 `/api/csrf`는 부를 때마다 다르게 가린 값을 준다. 어느 것을 보내도 통한다 |
| 실패 | 토큰이 없거나 틀리면 403 `INVALID_CSRF_TOKEN`. 화면은 `/api/csrf`를 다시 불러 한 번 더 보낼 수 있다 |

```json
GET /api/csrf
{"headerName":"X-XSRF-TOKEN","parameterName":"_csrf","token":"..."}
```

세션 행은 보지 않는다(요청마다 DB를 부르지 않는다). sid 쿠키가 남아 있지만 세션이 이미 끝났으면 CSRF는 지나고 뒤의 요청 인증(갱신)에서 401이 된다.

### 4-8. 로그아웃 (#87)

`POST /logout`만 받는다(CSRF 토큰·Origin 확인을 거친다). `GET` 등 다른 방식은 405 `METHOD_NOT_ALLOWED`(`Allow: POST`)이고 아무것도 지우지 않는다.

1. sid 쿠키의 세션 행을 지우고 ENDED 이벤트(사유 `logout`)를 낸다.
2. 쿠키 4개(sid·at·csrf·login)를 지운다. 같은 응답에서 같은 쿠키를 두 번 지우지 않는다.
3. 지운 행의 리프레시 토큰으로 Keycloak `end_session_endpoint`를 서버끼리 부른다(client 인증). ID 토큰은 쓰지 않는다.
4. 응답

| 경우 | 응답 |
|---|---|
| Keycloak 로그아웃이 됐다 | 화면 로그아웃 주소(`frontend.base-url` + `logout-success-path`)로 302 |
| sid 쿠키나 행이 없었다 | 같은 주소로 302. Keycloak은 부르지 않는다 |
| Keycloak이 거절했거나 닿지 않았다 | Keycloak 로그아웃 주소로 302: `client_id`, `post_logout_redirect_uri`(화면 로그아웃 주소), `state`. `id_token_hint`가 없으니 Keycloak이 브라우저에 로그아웃할지 묻고, 확인하면 화면으로 돌아온다 |

모든 응답에 `Cache-Control: no-store`. Keycloak 클라이언트의 Valid post logout redirect URIs에 화면 로그아웃 주소가 있어야 한다.

로컬 로그아웃(절대 상한, 갱신한 토큰이 세션과 맞지 않음)은 기본으로 Keycloak을 부르지 않는다(D13). `revoke-refresh-token-on-local-logout=true`면 그 세션의 리프레시 토큰을 Keycloak에서 폐기한다. `idle`·`refresh_failed`는 Keycloak 쪽 세션이 이미 끝났고, `decryption_failed`는 토큰을 풀 수 없어서 폐기하지 않는다.

### 4-9. back-channel 로그아웃 (#88)

Keycloak 세션이 끝나면(다른 앱에서 로그아웃, 관리자가 세션 삭제 등) Keycloak이 각 앱의 `POST /logout/connect/back-channel/keycloak`로 `logout_token`을 보낸다. 브라우저 요청이 아니므로 CSRF·Origin 확인을 거치지 않고, 토큰 서명으로 보호한다.

1. Spring Security의 back-channel 필터가 토큰을 검증한다: JWKS 서명, `iss`, `aud`에 client id, `iat`, `jti`, `events`에 back-channel 로그아웃 이벤트, `sub`나 `sid`, `nonce` 없음. 틀리면 400 `invalid_request`(D21).
2. `KeycloakBackChannelLogoutHandler`가 `sid`(= 로그인 때 행에 넣은 `kc_sid`)로 행을 모두 지우고 행마다 ENDED(`backchannel_logout`)를 낸다. 행이 없어도 200. `Cache-Control: no-store`.
3. 브라우저의 at 쿠키는 만료(Keycloak Access Token Lifespan, 테스트 60초)까지 스스로 통한다. 요청마다 DB를 보지 않기 때문이다. at가 끝나 갱신하려 할 때 행이 없으니 401이 된다(BCL-01).

Keycloak 클라이언트 설정: Backchannel logout URL `https://{api}/logout/connect/back-channel/keycloak`, Backchannel logout session required 켬. 앱이 Keycloak에서 닿는 주소여야 한다.

### 4-10. 세션 이벤트·감사 로그·MDC (#89)

세션 이벤트는 CREATED(로그인)·REFRESHED(갱신)·ENDED+사유(로그아웃, back-channel, 절대 상한, idle, 갱신 실패, 토큰 이상, 복호화 실패, 다시 로그인) 세 가지다. `KeycloakSessionEventListener` 빈과 Spring `@EventListener` 둘 다로 받는다. 기본 감사 로그는 로거 `com.ids.keycloak.security.audit`에 `[KSS] 세션 끝남 reason=… session=… user=앞8자…`처럼 남긴다(갱신은 DEBUG).

MDC는 v2와 같은 키·설정 이름·기본값이다(01 6절 `logging.*`, `trusted-proxy-count`). 바뀐 것(D22):

| 값 | v2 | v3 |
|---|---|---|
| `traceId` | `X-Request-Id`를 그대로 | 영문·숫자·`. _ : -` 128자 안일 때만, 아니면 새 UUID |
| `clientIp` | `trusted-proxy-count=-1`이면 첫 값 그대로 | IP에 쓰는 글자 64자 안만, 아니면 `unknown`. -1이면 기동 때 경고 한 번(요청마다 아님) |
| `username` | 그대로 | 값 가리기를 거친다(이메일이면 `a***@example.com`) |
| 제외 경로 | 요청 URI 전체로 맞춤 | 컨텍스트 경로를 뺀 앱 안 경로로 맞춤 |

토큰·쿠키 값은 로그 어디에도 넣지 않는다. E2E가 끝날 때 테스트 JVM의 모든 로그(라이브러리는 DEBUG까지, MDC·예외 포함)에서 JWT 모양과 샘플 앱이 준 쿠키 값을 찾는다(EVT-02).

## 5. 저장소와 암호 [제안]

### 5-1. 세션 행

표준 테이블 이름은 `auth_session`이다(설정으로 바꿀 수 있다). 앱이 열을 더 붙여도 라이브러리는 아래 열만 읽고 쓴다. 스키마 SQL은 라이브러리 jar(core)에 넣고(`kss/schema-postgresql.sql`, `kss/schema-h2.sql`), 실제 적용은 앱의 마이그레이션 도구(Flyway 등)가 한다. 스타터는 DB 초기화(Flyway 등)가 끝난 뒤 테이블과 열이 있는지 보고, 없으면 기동하지 않는다.

```sql
CREATE TABLE auth_session (
  id                  UUID         PRIMARY KEY,
  sid_hash            CHAR(64)     NOT NULL UNIQUE,  -- sid 쿠키의 SHA-256 (원문 저장 안 함)
  keycloak_user_id    VARCHAR(64)  NOT NULL,         -- 액세스 토큰 sub
  kc_sid              VARCHAR(64)  NOT NULL,         -- 액세스 토큰 sid (back-channel 로그아웃용)
  refresh_token_enc   BYTEA        NOT NULL,         -- AES-256-GCM
  enc_key_id          VARCHAR(32)  NOT NULL,
  refresh_expires_at  TIMESTAMPTZ  NOT NULL,
  created_at          TIMESTAMPTZ  NOT NULL,
  absolute_expires_at TIMESTAMPTZ  NOT NULL,
  refreshed_at        TIMESTAMPTZ
);
CREATE INDEX ix_auth_session_kc_sid ON auth_session (kc_sid);
CREATE INDEX ix_auth_session_user   ON auth_session (keycloak_user_id);
CREATE INDEX ix_auth_session_abs    ON auth_session (absolute_expires_at);
```

### 5-2. 키

| 용도 | 방식 |
|---|---|
| 리프레시 토큰 암호화 | AES-256-GCM. 키 id를 행에 적어서 키를 바꿔도 옛 행을 읽는다 |
| 로그인 임시 쿠키 | AES-256-GCM (암호화와 위조 확인을 함께) |
| CSRF 토큰 서명 | HMAC-SHA256(키, sid + 난수) |

설정에는 키 묶음 하나만 둔다(`keycloak.security.crypto.keys.{id}`, `active-key-id`). 용도별 키는 HKDF-SHA256으로 나눠 만든다. 키는 환경 변수나 비밀 저장소에서 넣고, 32바이트보다 짧거나 없으면 기동하지 않는다.

## 6. 설정 (`keycloak.security.*`) [제안]

```yaml
spring.security.oauth2.client:
  registration.keycloak: { client-id: myapp, client-secret: ${KC_SECRET}, scope: openid }
  provider.keycloak.issuer-uri: https://sso.example.com/realms/demo

keycloak:
  security:
    enabled: true                              # 끄면 자동 설정이 아무 것도 올리지 않는다
    registration-id: keycloak                  # 위 spring.security.oauth2.client 등록 id
    frontend:
      base-url: https://app.example.com        # (필수) CORS·Origin·로그인 뒤·로그아웃 뒤 주소. https만 (http는 localhost만)
      logout-success-path: /logged-out         # 기본 /
    cookie:
      app-name: myapp                          # __Host-myapp_sid ... 기본은 client id
    session:
      store: jdbc                              # jdbc | memory
      table-name: auth_session
      absolute-timeout: 12h
      refresh-reuse-window: 10s                # 동시 갱신 때 "방금 갱신함"으로 볼 시간
      cleanup-interval: 10m
    token:
      clock-skew: 30s
      required-audience: myapp                 # 기본은 client-id
    request:
      background-header: X-Background          # 이 헤더가 붙은 요청은 갱신하지 않는다
    csrf:
      endpoint: /api/csrf
    logout:
      revoke-refresh-token-on-local-logout: false
    permit-all-paths: [/api/public/**]
    auto-filter-chain: true                    # 기본 체인(맨 뒤, 모든 주소). 앱이 모든 주소를 자기 체인으로 지킬 때만 끈다 (D24)
    trusted-proxy-count: 0                     # 로그 clientIp용. 앞에 있는 믿을 프록시 수 (0이면 X-Forwarded-For를 안 봄)
    logging:                                   # MDC (v2와 같은 이름·기본값, 4-10)
      include-trace-id: true                   # X-Request-Id 또는 새 UUID
      return-trace-id-header: true             # 응답 X-Request-Id
      include-http-method: true
      include-request-uri: true
      include-client-ip: true
      include-user-agent: true
      max-user-agent-length: 256
      include-query-string: false
      max-query-length: 512
      include-response-metrics: false          # status·durationMs와 "request completed" 로그
      include-user-id: true
      include-username: true
      include-session-id: true                 # Keycloak sid (라이브러리 sid 쿠키 값 아님)
      exclude-patterns: [/actuator/**]
    crypto:
      active-key-id: k1                        # (필수)
      keys:
        k1: ${KSS_KEY_K1}                      # (필수) base64, 32바이트 이상. openssl rand -base64 32
```

기동 때 위 값을 모두 검사하고, 잘못된 것이 있으면 설정 이름을 모두 모아 알려 주며 기동하지 않는다(`KeycloakSecurityConfigurationException`, Boot는 FailureAnalyzer로 보여 준다). 비밀값은 오류·로그에 나오지 않는다. 검사 로직은 core의 `KeycloakSecuritySettings.Builder`에 있어서 Boot 없이 써도 같다.
