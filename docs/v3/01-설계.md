# 01. v3 설계

v3는 v2를 고치는 판이 아니라 새로 짜는 판이다. 라이브러리의 컨셉(아래 1절)은 그대로 두고, 안쪽 동작을 "BFF + JWT 쿠키 + DB 세션 행" 인증 방식으로 바꾼다.

표시: **[정함]** 이봉승이 정한 것 · **[제안]** 아직 결정 전, 이 판은 제안대로 진행 · **[확인 필요]** 실제 환경에서 확인할 것

---

## 1. 그대로 두는 컨셉 [정함]

v2 README 4·5장의 원칙을 그대로 지킨다. 지켜졌는지는 아키텍처 테스트(ArchUnit)로 빌드마다 확인한다(시나리오 EXT-01~05).

| # | 컨셉 | v3에서 지키는 법 |
|---|---|---|
| 1 | **커스텀은 열어 둔다.** 자동 설정의 빈마다 `@ConditionalOnMissingBean`을 붙여, 사용자가 같은 타입(또는 이름) 빈을 올리면 그것을 쓴다 | 4절 확장 지점 표의 빈은 모두 갈아끼울 수 있다. 빠진 빈이 없는지 테스트한다 |
| 2 | `Customizer<T>`로 덧붙인다 | `KeycloakHttpConfigurer`가 부분마다 `Customizer`를 받는다(로그인, 쿠키, CSRF, CORS, 로그아웃) |
| 3 | 보안상 꼭 필요한 곳이 아니면 `final`을 쓰지 않는다 | 공개 클래스에 `final`이 있으면 테스트가 실패한다. 예외는 값 객체(record)와 암호 처리 클래스뿐이다 |
| 4 | core(순수 Java)와 Servlet·Reactive 구현, 환경별 스타터를 나눈다 | 모듈 이름과 artifactId는 v2와 같다. core는 `jakarta.servlet`, `org.springframework.web`을 import하지 않는다 |
| 5 | 스타터 하나만 넣으면 설정 몇 줄로 돌아간다(Zero-config) | 필수 설정은 issuer, client id/secret, 화면 주소, 암호 키, DB뿐이다. 빠지면 기동 때 알려 준다 |

## 2. 버전 기준 [정함]

| 항목 | v3 기준 | v2 |
|---|---|---|
| Spring Boot | 4.1.x (Boot가 고르는 버전 그대로) | 3.5.9 |
| Spring Security | 7.1.x (Boot 4.1이 고르는 버전) | 6.5.x |
| Spring Framework | 7.0.x | 6.2.x |
| Java | 17 이상 (빌드 대상 17) [제안] | 17 |
| Gradle | 9.x [제안] | 8.5 |
| Keycloak (검증) | 26.8.x 최신 + 실제 운영 서버 판 [확인 필요] | - |

Boot 4.2(Security 7.2)가 나오면 CI에서 같이 돌려 본다. 같은 4.x라 코드는 그대로 가는 것을 목표로 한다.

v2 코드를 BOM만 4.1.2로 바꿔 컴파일해 보면 web·webflux 모듈에서 오류 3건이 먼저 나온다(`KeycloakHttpConfigurer`의 사라진 클래스 1건, `ReactiveAuthorizationManager.check` 제거 2건). 스타터 모듈은 이 오류 때문에 컴파일까지 가지 못해서, 실제로 고칠 곳은 더 있다. 동작 방식이 바뀌므로 올리기보다 새로 짠다.

## 3. 무엇이 바뀌나 (v2 → v3)

### 3-1. 인증 방식

| 항목 | v2 | v3 |
|---|---|---|
| 요청 인증 | 요청마다 Keycloak introspect + UserInfo 호출 | `at` 쿠키의 액세스 토큰(JWT)을 로컬에서 검증. Keycloak도 DB도 부르지 않는다 |
| 서버 상태 | HttpSession(메모리 또는 Redis)에 토큰 보관 | HttpSession을 만들지 않는다. 앱 DB의 세션 행에 리프레시 토큰만 암호화해서 둔다 |
| 쿠키 | `access_token`, `id_token` (이름 고정) | `__Host-{app}_sid` · `_at` · `_csrf` + 로그인 중에만 `_login` |
| ID 토큰 | 쿠키에 두고 요청마다 사용 | 저장하지 않는다. 로그인 때 Spring이 표준대로 확인만 한다 |
| 갱신 | introspect가 실패하면 갱신 | exp가 지났을 때만 갱신. 다른 검증 실패는 바로 로컬 로그아웃 |
| 동시 갱신 | 따로 막지 않음 | 세션 행 잠금으로 한 번만 갱신 |
| 세션 상한 | 미사용 30분(`session.timeout`) | 절대 상한(기본 12시간, 갱신 때 확인). 미사용은 Keycloak client의 Client Session Idle에 맡긴다 |
| CSRF | 세션 저장 토큰(기본) 또는 쿠키 | sid로 HMAC 서명한 double-submit 토큰 + Origin 확인. 토큰은 `GET /api/csrf`로 준다 |
| CORS | 없음 | 화면 origin 하나에만, 쿠키 허용 |
| PKCE | 없음 | S256 항상 |
| 로그인 임시 정보 | HttpSession | 암호화 쿠키(`_login`, 5분) |
| 로그아웃 | 결과와 상관없이 OIDC 로그아웃 주소로 이동 | 리프레시 토큰으로 Keycloak 로그아웃. 성공하면 화면으로, 실패할 때만 OIDC 로그아웃 주소로 |
| back-channel 로그아웃 | 색인 세션 저장소가 있어야 동작(메모리면 무동작) | `kc_sid`로 세션 행 삭제. 저장소와 상관없이 동작 |

### 3-2. 빼는 것 [제안]

v3 범위는 "브라우저 앱의 로그인"이다. 아래는 v3에서 뺀다. 필요하면 확장 지점으로 직접 붙이거나, 요청이 있을 때 3.x에서 다시 넣는다.

| v2 기능 | v3 | 이유 |
|---|---|---|
| Basic 인증 | 뺌 | 머신 클라이언트는 Keycloak service account로 받는 것이 맞다 |
| 토큰 발급 API(`/auth/token`, `/auth/refresh`, `/auth/logout`) | 뺌 | 비밀번호를 앱이 받는 방식(Direct access grants)은 쓰지 않는다 |
| Rate limit | 뺌 | 로그인은 Keycloak 화면에서 한다. 앱 API 제한은 게이트웨이나 앱이 정한다 |
| Keycloak Authorization Services 인가(`KeycloakAuthorizationManager`) | 뺌 | 인가는 앱이 한다 |
| introspect·UserInfo 호출 | 뺌 | 로컬 JWT 검증으로 바꾼다 |
| Redis·HttpSession 세션 저장소 | 뺌 | 세션 행(JDBC)으로 바꾼다. 다른 저장소는 `KeycloakSessionStore`를 구현해 붙인다 |
| 역할 → 권한 매핑 | 확장 지점만 둔다(기본은 권한 없음) | 토큰에 역할을 싣지 않는 것이 기본이다. 3.1에서 선택 기능으로 다시 넣을 수 있다 |
| `io.github.l-dxd:keycloak-client` 의존 | 뺌 | 갱신·로그아웃 호출은 Spring Security OAuth2 Client와 `RestClient`로 한다. reactor-netty, jjwt, Jackson 2가 따라오지 않는다 |

남기는 것: MDC 로깅(사내 표준 위임 구조 포함), 오류 응답 형식(`error.*` 설정), 감사 로그.

### 3-3. Servlet 먼저 [제안]

3.0.0은 Servlet(Spring MVC)만 낸다. WebFlux 모듈은 3.1.0에서 같은 core로 다시 짠다. 모듈과 artifactId 자리는 그대로 둔다.

## 4. 구조

### 4-1. 모듈

| 모듈 (artifactId 그대로) | 담는 것 |
|---|---|
| `keycloak-spring-security-core` | 설정 값 객체, 세션 모델과 `KeycloakSessionStore`(JDBC·메모리 구현과 스키마 SQL 포함), 정리 작업, 암호(`TokenCipher`, sid 해시, CSRF 서명), 토큰 클레임 규칙, 오류 코드, 세션 이벤트, MDC 키. Spring Web·Servlet 의존 없음 (JDBC 저장소를 WebFlux와 같이 쓰려고 core에 둔다, D16) |
| `keycloak-spring-security-web` | Servlet 필터와 처리기: 요청 인증, 갱신, 로그인 성공·실패, 로그인 임시 쿠키 저장소, CSRF 저장소, `/api/csrf`, Origin 확인, 로그아웃, back-channel 로그아웃, 쿠키 쓰기, `KeycloakHttpConfigurer` |
| `keycloak-spring-security-web-starter` | 자동 설정, 설정 바인딩(`keycloak.security.*`), 기동 때 설정·세션 테이블 검사 |
| `keycloak-spring-security-webflux(-starter)` | 3.1.0 (3.0.0에서는 빌드에서 뺀다) |
| `integration-tests/servlet-app` | 검증용 샘플 앱(가상 프로젝트). 03 문서 |

패키지 루트는 `com.ids.keycloak.security`, groupId는 `io.github.l-dxd` 그대로다.

### 4-2. 요청 한 번의 순서 (Servlet)

```text
CorsFilter (Spring Security보다 앞)
→ KeycloakOriginFilter          상태 바꾸는 요청의 Origin/Referer 확인
→ CsrfFilter                     sid 서명 double-submit 확인
→ KeycloakAccessTokenFilter      at 쿠키 JWT 로컬 검증 → SecurityContext
     ├ exp 만료·쿠키 없음 → KeycloakRefreshService (세션 행 잠금 → Keycloak 갱신)
     └ 그 밖의 검증 실패 → 로컬 로그아웃(행·쿠키 삭제) → 401
→ AuthorizationFilter            permit-all 경로 / 그 밖은 로그인 필요
```

로그인(`/oauth2/authorization/keycloak`, `/login/oauth2/code/keycloak`)은 Spring Security `oauth2Login`을 쓰고, 저장소와 처리기만 바꿔 끼운다. 로그아웃(`POST /logout`)과 back-channel 로그아웃(`/logout/connect/back-channel/keycloak`)은 라이브러리 처리기로 받는다.

### 4-3. 확장 지점 (커스텀 열어 두기)

모두 자동 설정에 `@ConditionalOnMissingBean`으로 올린다. 사용자가 같은 빈을 올리면 그것을 쓴다.

| 빈 (타입) | 기본 구현 | 바꾸는 예 |
|---|---|---|
| `KeycloakSessionStore` | `JdbcKeycloakSessionStore`(PostgreSQL, H2) · 설정으로 `InMemoryKeycloakSessionStore` | 다른 DB, 테이블 구조가 다른 앱 |
| `KeycloakAccessTokenValidator` (`JwtDecoder` 감싼 것) | JWKS + RS256 + iss + aud/azp + typ + 시간 오차 30초. 결과는 통과·만료(갱신)·실패(로컬 로그아웃)·JWKS 못 받음(503) | 검증 규칙 추가 |
| `JwkSetFetcher` | JWKS를 HTTP로 받기(연결 2초·읽기 3초). 모르는 kid면 다시 받되 1분에 한 번 | 프록시, 타임아웃 |
| `KeycloakPrincipalConverter` | `Jwt` → `KeycloakPrincipal`(sub, sid, azp, 선택 클레임), 권한 없음 | 역할을 권한으로, 앱 사용자 테이블 조회 |
| `KeycloakTokenClient` | Spring OAuth2 Client 갱신 + `RestClient` 로그아웃 | 프록시, 타임아웃, 재시도 |
| `TokenCipher` | AES-256-GCM, 키 id로 교체 | KMS·HSM |
| `KeycloakCookieWriter` | `__Host-{app}_*`, Secure, HttpOnly, SameSite=Lax, Path=/ | 쿠키 이름 규칙 |
| `CsrfTokenRepository` | `SignedDoubleSubmitCsrfTokenRepository` | - |
| `CorsConfigurationSource` | 화면 origin 하나 | origin 여러 개 |
| `LoginReturnPathResolver` | `return` 파라미터, 상대 경로만 | 경로 화이트리스트 |
| `KeycloakLoginSuccessHandler` | 세션 행 만들기 → sid·at·csrf 쿠키 → 화면 주소로 302. 메서드(`endPreviousSession`, `writeCookies`, `redirectUrl`)를 덮어쓸 수 있다 | 로그인 직후 앱 사용자 테이블 갱신 |
| `KeycloakLoginFailureHandler` | login 쿠키를 지우고 화면 `/?login_error=코드`로 302 | 오류 화면 주소 |
| `KeycloakAuthenticationEntryPoint` / `KeycloakAccessDeniedHandler` / `KeycloakErrorResponseWriter` | 401·403·503 JSON | 앱 오류 형식 |
| `KeycloakSessionEventListener` | 감사 로그 `KeycloakSessionAuditLogger`(로거 `com.ids.keycloak.security.audit`, 토큰 값 없음, 사용자 id 앞 8자). 이 빈을 올리면 기본 감사 로그 대신 그것이 받는다. Spring `@EventListener`로도 받는다 | 감사 테이블 저장 |
| `KeycloakLocalLogoutHandler` | sid 쿠키의 행 삭제 → 쿠키 4개 삭제 → ENDED 이벤트(사유). Keycloak은 부르지 않는다. 토큰 검증 실패·갱신 실패가 쓴다 | 로컬 로그아웃 때 앱 캐시 비우기 |
| `KeycloakSessionCleaner` | `session.cleanup-interval`마다 데몬 스레드 하나로 끝난 행을 500개씩 지우고 ENDED 이벤트(사유 `absolute`·`idle`)를 낸다 | DB 배치 작업으로 대신 |
| `Clock` (이름 `keycloakSecurityClock`) | 시스템 시계 | 테스트 |
| `SecurityFilterChain` (이름 `keycloakSecurityFilterChain`) | 기본 체인 | 사용자 체인 + `KeycloakHttpConfigurer` |

```java
@Bean
SecurityFilterChain api(HttpSecurity http) throws Exception {
    return http
        .securityMatcher("/api/**", "/oauth2/**", "/login/oauth2/**", "/logout/**")
        .authorizeHttpRequests(a -> a.requestMatchers("/api/public/**").permitAll().anyRequest().authenticated())
        .with(KeycloakHttpConfigurer.keycloak(), k -> k
            .cookies(c -> c.appName("myapp"))
            .cors(c -> c.allowedHeader("X-Trace-Id")))
        .build();
}
```

### 4-4. 요청 인증 (#84)

`KeycloakAccessTokenFilter`는 빈이 아니다(서블릿 필터로 따로 등록되어 보안 체인 밖에서 돌지 않게). `KeycloakHttpConfigurer`가 Basic 인증 자리 앞에 넣고, 바꾸려면 설정기의 `accessTokenFilter(...)`를 덮어쓰거나 필터가 쓰는 빈을 바꾼다.

| at 쿠키 검증 결과 | 하는 일 |
|---|---|
| 통과 | `KeycloakPrincipalConverter`가 만든 인증을 보안 컨텍스트(요청 속성)에 넣는다. 기본은 `KeycloakAuthenticationToken`(principal `KeycloakPrincipal`: sub·sid·azp·클레임, credentials는 `Jwt`, 권한 없음). 세션 행을 보지 않는다 |
| 쿠키 없음, 만료 | 로그인 안 한 채로 넘긴다. 갱신은 #85에서 이 자리에 붙는다 |
| 그 밖의 실패(서명, iss, aud, typ …) | 로컬 로그아웃(`KeycloakLocalLogoutHandler`, 사유 `invalid_token`) 뒤 로그인 안 한 채로 넘긴다. 갱신하지 않는다 |
| JWKS를 못 받음 | 로그아웃하지 않고 503 `KEYCLOAK_UNAVAILABLE` |

로그인 필요 여부는 뒤의 인가가 정한다(permit-all 경로는 그대로 통과, 그 밖은 401). 앞에서 다른 방식으로 이미 인증했으면 건드리지 않는다. 변환기가 `AuthenticationException`을 던지면 그 요청만 로그인 안 한 것으로 본다. 컨트롤러는 `@AuthenticationPrincipal KeycloakPrincipal user`로 받는다. `getName()`은 sub다.

### 4-5. 로그인과 오류 응답 (#83)

로그인은 Spring Security `oauth2Login`에 아래만 바꿔 끼운다. HttpSession은 만들지 않는다(보안 컨텍스트는 요청 속성에만, 요청 캐시 없음). `sessionCreationPolicy(STATELESS)`는 쓰지 않는다: 설정 순서 때문에 `SessionManagementFilter`가 켜져 로그인한 요청마다 세션을 만든다(REQ-05에서 발견).

| 단계 | 하는 일 |
|---|---|
| `GET /oauth2/authorization/keycloak?return=/경로` | PKCE S256·state·nonce를 만들고, 인가 요청과 돌아갈 경로를 `__Host-{app}_login` 쿠키(5분)에 암호화해 담는다(`KeycloakAuthorizationRequestRepository`, HKDF 용도 `login-state`). 만든 시각은 쿠키 안에 두고 서버 시계로 5분을 다시 본다 |
| 돌아갈 경로 | `/`로 시작하는 상대 경로만. `//`, `\`, 제어 문자, 2048자 넘는 값, 절대 주소는 모두 `/` |
| `GET /login/oauth2/code/keycloak` | Spring이 code 교환과 ID 토큰(서명·nonce)을 확인한다. UserInfo는 부르지 않는다. 받은 토큰은 요청 안에서만 쓰고 어디에도 두지 않는다 |
| 성공 | 액세스 토큰을 로컬 검증 규칙으로 다시 보고(sub·sid 필수), 예전 sid 쿠키의 행을 지운 뒤(사유 `relogin`) 새 행을 만든다. sid·csrf 쿠키는 절대 상한까지, at 쿠키는 토큰 남은 시간까지. 화면 주소 + 돌아갈 경로로 302 |
| 실패 | login 쿠키를 지우고 화면 `/?login_error=코드`로 302. 세션 행은 만들지 않는다 |

로그인 실패 코드: `invalid_state`(login 쿠키 없음·5분 지남·state 다름), `access_denied`(Keycloak에서 취소), `invalid_token`(받은 토큰이 검증 규칙에 맞지 않음), `login_failed`(그 밖).

401·403·503 본문은 `KeycloakErrorCode` 하나로 정한다. 401에만 로그인 주소가 붙는다(context-path 포함).

```json
{"code":"AUTHENTICATION_REQUIRED","message":"로그인이 필요합니다.","loginUrl":"/oauth2/authorization/keycloak"}
{"code":"ACCESS_DENIED","message":"..."}
{"code":"KEYCLOAK_UNAVAILABLE","message":"..."}
```

CSRF 토큰 값은 `키id.난수.HMAC-SHA256(sid, 난수)`이다(HKDF 용도 `csrf`). 로그인 때 csrf 쿠키에 넣고, 확인은 #86에서 켠다.

## 5. 저장소와 암호 [제안]

### 5-1. 세션 행

표준 테이블 이름은 `auth_session`이다(설정으로 바꿀 수 있다). 앱이 열을 더 붙여도 라이브러리는 아래 열만 읽고 쓴다. 스키마 SQL은 라이브러리 jar(core)에 넣고(`kss/schema-postgresql.sql`, `kss/schema-h2.sql`), 실제 적용은 앱의 마이그레이션 도구(Flyway 등)가 한다. 스타터는 DB 초기화(Flyway 등)가 끝난 뒤 테이블과 열이 있는지 보고, 없으면 기동하지 않는다.

```sql
CREATE TABLE auth_session (
  id                  UUID         PRIMARY KEY,
  sid_hash            CHAR(64)     NOT NULL UNIQUE,  -- sid 쿠키의 SHA-256 (원문 저장 안 함)
  keycloak_user_id    VARCHAR(64)  NOT NULL,         -- 액세스 토큰 sub
  kc_sid              VARCHAR(64)  NOT NULL,         -- 액세스 토큰 sid (back-channel 로그아웃용)
  refresh_token_enc   BYTEA        NOT NULL,         -- AES-256-GCM
  enc_key_id          VARCHAR(32)  NOT NULL,
  refresh_expires_at  TIMESTAMPTZ  NOT NULL,
  created_at          TIMESTAMPTZ  NOT NULL,
  absolute_expires_at TIMESTAMPTZ  NOT NULL,
  refreshed_at        TIMESTAMPTZ
);
CREATE INDEX ix_auth_session_kc_sid ON auth_session (kc_sid);
CREATE INDEX ix_auth_session_user   ON auth_session (keycloak_user_id);
CREATE INDEX ix_auth_session_abs    ON auth_session (absolute_expires_at);
```

### 5-2. 키

| 용도 | 방식 |
|---|---|
| 리프레시 토큰 암호화 | AES-256-GCM. 키 id를 행에 적어서 키를 바꿔도 옛 행을 읽는다 |
| 로그인 임시 쿠키 | AES-256-GCM (암호화와 위조 확인을 함께) |
| CSRF 토큰 서명 | HMAC-SHA256(키, sid + 난수) |

설정에는 키 묶음 하나만 둔다(`keycloak.security.crypto.keys.{id}`, `active-key-id`). 용도별 키는 HKDF-SHA256으로 나눠 만든다. 키는 환경 변수나 비밀 저장소에서 넣고, 32바이트보다 짧거나 없으면 기동하지 않는다.

## 6. 설정 (`keycloak.security.*`) [제안]

```yaml
spring.security.oauth2.client:
  registration.keycloak: { client-id: myapp, client-secret: ${KC_SECRET}, scope: openid }
  provider.keycloak.issuer-uri: https://sso.example.com/realms/demo

keycloak:
  security:
    enabled: true                              # 끄면 자동 설정이 아무 것도 올리지 않는다
    registration-id: keycloak                  # 위 spring.security.oauth2.client 등록 id
    frontend:
      base-url: https://app.example.com        # (필수) CORS·Origin·로그인 뒤·로그아웃 뒤 주소. https만 (http는 localhost만)
      logout-success-path: /logged-out         # 기본 /
    cookie:
      app-name: myapp                          # __Host-myapp_sid ... 기본은 client id
    session:
      store: jdbc                              # jdbc | memory
      table-name: auth_session
      absolute-timeout: 12h
      refresh-reuse-window: 10s                # 동시 갱신 때 "방금 갱신함"으로 볼 시간
      cleanup-interval: 10m
    token:
      clock-skew: 30s
      required-audience: myapp                 # 기본은 client-id
    request:
      background-header: X-Background          # 이 헤더가 붙은 요청은 갱신하지 않는다
    csrf:
      endpoint: /api/csrf
    logout:
      revoke-refresh-token-on-local-logout: false
    permit-all-paths: [/api/public/**]
    crypto:
      active-key-id: k1                        # (필수)
      keys:
        k1: ${KSS_KEY_K1}                      # (필수) base64, 32바이트 이상. openssl rand -base64 32
```

기동 때 위 값을 모두 검사하고, 잘못된 것이 있으면 설정 이름을 모두 모아 알려 주며 기동하지 않는다(`KeycloakSecurityConfigurationException`, Boot는 FailureAnalyzer로 보여 준다). 비밀값은 오류·로그에 나오지 않는다. 검사 로직은 core의 `KeycloakSecuritySettings.Builder`에 있어서 Boot 없이 써도 같다.
