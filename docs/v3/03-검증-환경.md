# 03. 검증 환경

v3는 "실제로 붙여 봤을 때 되는가"로 검증한다. 가짜 Keycloak을 흉내 내지 않고, 실제 Keycloak과 PostgreSQL을 띄우고, 실제 Spring Boot 앱(샘플 앱)에 라이브러리를 넣어서 02의 시나리오를 HTTP로 돌린다.

## 1. 세 단계

| 단계 | 무엇을 | 어디서 | 명령 |
|---|---|---|---|
| 단위 | 클래스 하나 (검증 규칙, 암호, 쿠키 쓰기, 경로 검사) | 각 모듈 `src/test` | `./gradlew test` |
| 통합 | Spring 컨텍스트 (자동 설정, 확장 지점, 저장소 계약, 기동 검사) | 각 모듈 + 샘플 앱 | `./gradlew test` |

## 4. 브라우저처럼 HTTP로 돌리기

E2E 테스트는 브라우저를 띄우지 않고 "쿠키 상자 + 리다이렉트를 하나씩 따라가는 HTTP 클라이언트"로 돌린다. Set-Cookie 속성, 302 주소, 쿼리 파라미터를 그대로 확인할 수 있고 빠르다.

1. 앱의 `/oauth2/authorization/keycloak`을 부르고 302를 따라 Keycloak 로그인 화면을 받는다.
2. 로그인 폼(`#kc-form-login`)의 action에 아이디·비밀번호를 POST한다.
3. 콜백 302를 따라가고, 마지막 302가 화면 주소인지 본다.
4. 이후 요청은 `Origin: https://app.kss.test`를 붙여 화면에서 부른 것처럼 보낸다.

`BrowserClient`의 도움 함수: `login`(1~3), `authorize`(2까지만. 콜백을 바꿔 부르는 LOGIN-05), `ssoLogin`(이미 Keycloak에 로그인한 브라우저. Keycloak이 화면 없이 콜백으로 보내는지 확인, LOGIN-06·08). 세션 행과 토큰은 `AppSessions`로 본다(행 수, 앱 암호로 푼 리프레시 토큰, JWT 본문). 샘플 앱에는 테스트에서만 세 가지를 더 넣는다: 앱이 DB에 보낸 SQL 기록(`SqlRecorder`, REQ-03), 만들어진 HttpSession 수와 만든 곳(`HttpSessionCounter`, REQ-05), 그리고 시계(6절). 로그는 `LogCapture`로 모은다(감사 로그 사유, REQ-04). "Keycloak을 몇 번 불렀나"는 Keycloak 사용자 이벤트로 센다. 배포판 Keycloak은 이전 실행의 이벤트가 쌓이므로 전체 개수를 비교하지 않고, 이 로그인의 Keycloak 세션(`kc_sid`) 이벤트(`KeycloakAdmin.sessionEvents`, REFRESH-02) 또는 테스트 시작 뒤의 이벤트(`eventsSince`, JWT-09)만 센다.

갱신(#85)에 쓰는 것: 같은 쿠키로 요청 여러 개를 한꺼번에 보내는 `BrowserClient.getConcurrently`(REFRESH-02), 테스트마다 만들고 지우는 임시 사용자(`KeycloakAdmin.createUser`·`setUserEnabled`·`deleteUser`, REFRESH-04. 공용 사용자 alice·bob은 막지 않는다), 갱신 때만 Keycloak에 닿지 않게 하는 `KeycloakOutage`(REFRESH-06, 6절).

로그아웃(#87)·back-channel(#88): Keycloak이 실패하는 경우는 `KeycloakOutage`로 만든다(LOGOUT-02. 로컬 Keycloak 26.8.2는 리프레시 토큰을 폐기한 뒤에도 그 토큰의 로그아웃에 성공으로 답한다). 잘못된 logout_token(BCL-02~04)은 Keycloak이 만들어 주지 않으므로, 실행마다 새 RSA 키를 만들어 테스트 realm에 우선순위 1인 서명 키 `kss-e2e-logout-token-key`로 넣고(Keycloak은 계속 자기 키로 서명하고 이 키는 JWKS에만 나온다) 그 키로 직접 서명한다(`E2eLogoutTokens`). 앱이 JWKS를 받기 전에 넣어야 하므로 `SampleApps`가 앱을 띄우기 전에 넣는다. Keycloak 세션 확인은 `KeycloakAdmin.userSessions`.

CSRF·CORS(#86): 다른 화면은 Origin 값 `https://evil.kss.test`로 흉내 낸다(화면과 같은 사이트라 SameSite만으로는 못 막는 경우. 헤더 값일 뿐이라 이름을 풀 필요는 없다). 사전 확인은 `BrowserClient.options`로 보낸다.

주소 이름은 `app.kss.test`, `api.kss.test`, `sso.kss.test`를 쓴다. `.test`는 인터넷에 없는 예약 이름이라 밖으로 새지 않는다. 이름은 JVM 옵션 `-Djdk.net.hosts.file`로 그 JVM 안에서만 127.0.0.1로 푼다. `/etc/hosts`나 외부 DNS는 건드리지 않는다.

- 테스트 JVM(샘플 앱 + 테스트 클라이언트): `e2eTest` 작업이 `build/e2e/hosts`를 만들어 넘긴다. 이 JVM은 이 파일에 있는 이름만 풀 수 있으므로, 밖에 띄운 Keycloak·DB 주소는 `localhost`·`127.0.0.1`·`*.kss.test`로 준다.
- Keycloak: Testcontainers면 추가 호스트 `api.kss.test → host-gateway`, 배포판이면 `start-local.sh`가 같은 hosts 파일을 `JAVA_OPTS_APPEND`로 넘긴다. `HTTPS_PROXY`가 잡힌 곳에서는 Keycloak이 back-channel 로그아웃 요청을 프록시로 보내 실패하므로(Keycloak은 이 환경 변수를 따른다), `start-local.sh`가 `NO_PROXY`에 `*.kss.test` 세 이름을 더한다.

`__Host-` 쿠키에는 HTTPS가 필요하므로 샘플 앱은 테스트 CA 인증서로 HTTPS를 연다. 테스트 클라이언트(`BrowserClient`)는 그 CA만 믿고, 리다이렉트를 저절로 따라가지 않으며, 쿠키 상자를 직접 가진다(http 응답이 준 Secure 쿠키는 브라우저처럼 버린다).

실제 브라우저에서만 보이는 것(SameSite 동작, `__Host-` 규칙)은 Playwright(Chromium)로 따로 한 번 확인한다. 4-1절.

### 4-1. 실제 브라우저 확인

`integration-tests/browser/cookie-check.mjs`. 빌드에 묶지 않은 손 확인이다. 쿠키·CORS·CSRF 처리를 바꿀 때와 배포 전에 한 번 돌린다.

```bash
# Keycloak을 띄운 뒤(5절), 샘플 앱을 띄운다. 이름 풀이는 E2E와 같은 hosts 파일
JAVA_TOOL_OPTIONS="-Djdk.net.hosts.file=$PWD/integration-tests/servlet-app/build/e2e/hosts" \
  ./gradlew :integration-tests:servlet-app:bootRun
# 다른 창에서 (Playwright가 깔린 Node. HTTPS_PROXY 같은 프록시 환경 변수는 지운다)
node integration-tests/browser/cookie-check.mjs
```

## 5. 돌리는 법

```bash
# Docker가 있으면 (CI도 같음): Keycloak·PostgreSQL을 Testcontainers로 띄운다 (E2E-01)
./gradlew :integration-tests:servlet-app:e2eTest

# Docker가 없으면 (E2E-02): Keycloak은 배포판, DB는 아무 PostgreSQL
integration-tests/keycloak/start-local.sh          # 다른 터미널. http://sso.kss.test:8180
KSS_E2E_KEYCLOAK_URL=http://sso.kss.test:8180 \
KSS_E2E_DB_URL=jdbc:postgresql://localhost:5432/kss KSS_E2E_DB_USERNAME=kss KSS_E2E_DB_PASSWORD=kss \
./gradlew :integration-tests:servlet-app:e2eTest

# 오래 걸리는 시나리오(@Tag("slow"))까지
./gradlew :integration-tests:servlet-app:e2eTest -PincludeSlow

# 같은 배포판 Keycloak을 다른 작업 폴더(git worktree 등)에서 쓸 때: 그 Keycloak이 믿는 인증서 폴더를 준다
KSS_E2E_TLS_DIR=<start-local.sh를 돌린 폴더>/integration-tests/servlet-app/build/e2e/tls ./gradlew :integration-tests:servlet-app:e2eTest
```

E2E는 테스트 클래스를 이름순으로 돌린다(`src/test/resources/junit-platform.properties`). 맨 끝의 `E2eZzLogHygieneTest`(EVT-02)가 그때까지 테스트 JVM에 남은 모든 로그를 본다. 로그는 샘플 앱이 뜬 뒤 루트 로거에 붙인 `E2eLogRecorder`가 모으고, 라이브러리 로거는 DEBUG로 둔다.

새 작업 폴더의 `build/e2e/tls`는 Gradle이 처음 돌 때 지우고 새 CA로 다시 만든다. 그러면 배포판 Keycloak(처음 띄울 때의 CA를 믿음)이 샘플 앱 HTTPS를 믿지 못해 back-channel 로그아웃(BCL-01)만 실패한다. 미리 복사해 두어도 지워지므로 `KSS_E2E_TLS_DIR`로 준다.

`./gradlew build`(`test`)는 E2E를 돌리지 않는다. 세션 저장소 계약 테스트(STORE-01·06)는 `KSS_TEST_DB_URL`(+ `_USERNAME`, `_PASSWORD`)을 주면 PostgreSQL에도 돈다(테스트마다 스키마를 따로 만들고 지운다). CI는 PostgreSQL 서비스를 붙여 늘 돌린다. 다른 Keycloak 판은 `KSS_E2E_KEYCLOAK_VERSION`으로 고른다(Testcontainers). 배포판 Keycloak은 `data/`에 realm을 저장하므로, realm 파일을 고쳤으면 그 폴더를 지우고 다시 띄운다.

## 6. 시간이 걸리는 시나리오

| 시나리오 | 방법 |
|---|---|
| 액세스 토큰 만료 | at 쿠키를 지워서 바로 만든다(브라우저가 Max-Age 지난 쿠키를 버린 것과 같다). 앱 시계를 돌리면 Keycloak이 새로 준 토큰까지 만료로 보이므로 쓰지 않는다. 실제 만료는 기다리는 테스트 하나(`@Tag("slow")`)만 둔다 |
| 절대 상한, login 쿠키 5분 | 앱 쪽 시계(`keycloakSecurityClock`)를 테스트에서 앞으로 돌린다. E2E 하네스가 앱마다 `E2eClock`을 이 이름으로 올리고(`app.clock().advance(…)`), 테스트가 끝나면 `reset()`한다 |
| Client Session Idle | realm 테스트값 2분. 빠른 테스트는 앱 시계를 행의 `refresh_expires_at` 뒤로 돌린다(REFRESH-05). 실제로 기다려서 Keycloak도 같은 리프레시 토큰을 거절하는지 보는 테스트는 `@Tag("slow")`(약 2분) |
| 갱신 때 Keycloak 멈춤 | 공용 Keycloak을 멈추면 다른 테스트와 두 번째 앱이 흔들리므로, 샘플 앱의 `KeycloakTokenClient` 빈을 `KeycloakOutage`로 감싸 켜 둔 동안만 같은 설정의 기본 클라이언트를 닫힌 포트로 보낸다. 연결 거부는 실제로 일어나고 라이브러리 코드는 그대로 돈다(REFRESH-06) |

## 7. 결과 남기기

- PR마다 CI가 단위·통합·E2E를 돌리고 테스트 보고서를 붙인다.
- 테스트 이름은 시나리오 번호로 시작한다. 이슈의 수용 조건 체크는 테스트 이름으로 맞춘다.
- 이슈를 닫을 때 그 이슈 시나리오의 통과 결과(테스트 보고서 링크)를 이슈에 남긴다.
