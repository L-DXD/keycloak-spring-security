# 03. 검증 환경

v3는 "실제로 붙여 봤을 때 되는가"로 검증한다. 가짜 Keycloak을 흉내 내지 않고, 실제 Keycloak과 PostgreSQL을 띄우고, 실제 Spring Boot 앱(샘플 앱)에 라이브러리를 넣어서 02의 시나리오를 HTTP로 돌린다.

## 1. 세 단계

| 단계 | 무엇을 | 어디서 | 명령 |
|---|---|---|---|
| 단위 | 클래스 하나 (검증 규칙, 암호, 쿠키 쓰기, 경로 검사) | 각 모듈 `src/test` | `./gradlew test` |
| 통합 | Spring 컨텍스트 (자동 설정, 확장 지점, 저장소 계약, 기동 검사) | 각 모듈 + 샘플 앱 | `./gradlew test` |
| E2E | 샘플 앱 + 실제 Keycloak + PostgreSQL, 브라우저처럼 HTTP로 | `integration-tests/servlet-app` | `./gradlew :integration-tests:servlet-app:e2eTest` |

## 2. 샘플 앱 (가상 프로젝트)

`integration-tests/servlet-app`을 v3용으로 새로 만든다. 실제 앱이 라이브러리를 쓰는 모습 그대로 둔다.

| 항목 | 값 |
|---|---|
| 의존성 | `keycloak-spring-security-web-starter`(프로젝트 의존), `spring-boot-starter-webmvc`, JDBC, PostgreSQL 드라이버, Flyway |
| 스키마 | Flyway `V1__auth_session.sql` = 스타터의 `kss/schema-postgresql.sql` 그대로 + 앱 열 하나(`display_name`, STORE-07용) |
| 주소 | `GET /api/me`(로그인 필요), `GET /api/public/ping`(허용), `POST /api/items`(로그인 + CSRF), 로그아웃 뒤 화면 대신 `GET /logged-out` 흉내 |
| 설정 | 01 설계 6절과 같은 모양. 테스트 설정만 액세스 토큰 60초, 절대 상한 3분 |
| 두 번째 앱 | 같은 코드에 프로필 `demo2`(client `demo2`, 앱 이름 `demo2`)로 한 벌 더 띄워 SSO·back-channel 시나리오에 쓴다 |

## 3. Keycloak

| 항목 | 값 |
|---|---|
| 판 | 26.8.2 (지금 최신). 운영 Keycloak 판을 확인하면 그 판도 CI에 더한다 [확인 필요] |
| 띄우는 법 | CI·Docker가 있으면 Testcontainers(`quay.io/keycloak/keycloak`). Docker가 없으면 배포판을 내려받아 `kc.sh start-dev`로 띄우고 주소를 환경 변수로 준다 (`integration-tests/keycloak/start-local.sh`) |
| realm | `integration-tests/keycloak/realm-kss-demo.json`을 기동 때 넣는다 |
| client `demo`, `demo2` | 비공개, Standard flow만, PKCE S256 강제, redirect URI `https://api.kss.test/login/oauth2/code/keycloak` 하나, post logout redirect `https://app.kss.test/` 하나, back-channel 주소, session required, Client Session Idle 2분 / Max 3분(테스트값), audience mapper, Full scope 끔 |
| 사용자 | `alice`, `bob` (테스트 비밀번호, 파일에만) |
| 인증서 | 샘플 앱은 테스트 CA로 만든 인증서로 HTTPS를 연다. Keycloak은 back-channel 호출을 위해 그 CA를 신뢰하도록 truststore를 받는다 |
| 이벤트 | 로그인·토큰·로그아웃 이벤트 저장을 켜서 "Keycloak을 몇 번 불렀나"를 센다 (JWT-09, REFRESH-02) |

## 4. 브라우저처럼 HTTP로 돌리기

E2E 테스트는 브라우저를 띄우지 않고 "쿠키 상자 + 리다이렉트를 하나씩 따라가는 HTTP 클라이언트"로 돌린다. Set-Cookie 속성, 302 주소, 쿼리 파라미터를 그대로 확인할 수 있고 빠르다.

1. 앱의 `/oauth2/authorization/keycloak`을 부르고 302를 따라 Keycloak 로그인 화면을 받는다.
2. 로그인 폼(`#kc-form-login`)의 action에 아이디·비밀번호를 POST한다.
3. 콜백 302를 따라가고, 마지막 302가 화면 주소인지 본다.
4. 이후 요청은 `Origin: https://app.kss.test`를 붙여 화면에서 부른 것처럼 보낸다.

주소 이름은 `app.kss.test`, `api.kss.test`, `sso.kss.test`를 쓴다. `.test`는 인터넷에 없는 예약 이름이라 밖으로 새지 않는다. 테스트 HTTP 클라이언트는 이 이름들을 직접 127.0.0.1로 풀고(외부 DNS를 쓰지 않음), Keycloak 쪽은 back-channel 호출을 위해 Testcontainers의 추가 호스트(로컬이면 `/etc/hosts`)로 같은 이름을 준다. `__Host-` 쿠키에는 HTTPS가 필요하므로 샘플 앱은 테스트용 자체 서명 인증서로 HTTPS를 연다.

실제 브라우저에서만 보이는 것(SameSite 동작, `__Host-` 거절)은 3.0.0 전에 Playwright로 한 번 확인하고 결과를 PR에 남긴다.

## 5. 시간이 걸리는 시나리오

| 시나리오 | 방법 |
|---|---|
| 액세스 토큰 만료 | at 쿠키를 지워서 바로 만든다. 실제 만료는 60초 기다리는 테스트 하나만 둔다 |
| 절대 상한 | 앱 쪽 시계(`keycloakSecurityClock`)를 테스트에서 앞으로 돌린다 |
| Client Session Idle | realm 테스트값 2분. 이 테스트만 `@Tag("slow")`로 나눈다 |

## 6. 결과 남기기

- PR마다 CI가 단위·통합·E2E를 돌리고 테스트 보고서를 붙인다.
- 테스트 이름은 시나리오 번호로 시작한다. 이슈의 수용 조건 체크는 테스트 이름으로 맞춘다.
- 이슈를 닫을 때 그 이슈 시나리오의 통과 결과(테스트 보고서 링크)를 이슈에 남긴다.
